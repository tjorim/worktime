#1098 sync

Outbox flush clears the whole key, dropping changes queued mid-push

Resolved

dequeueAndMergeSyncOutbox returns a commit that calls clearSyncOutbox — a removeItem on the entire key — rather than removing the entries it dequeued. A write whose immediate push fails during an in-flight flush is appended to that same key, then deleted when the flush commits. The optimistic write still shows in the UI and sync reports healthy, so nothing surfaces the loss and nothing retries it.

Record the snapshot length and drop exactly that many entries from the front — safe because appends only ever go to the end. Same treatment on the quarantine path.
frontend/src/utils/syncClient.ts:1246 syncClient.ts:1112 hooks/useOngoingSync.ts:280 useOngoingSync.ts:336
commit() now removes exactly the dequeued entries via a content-keyed multiset — clearSyncOutbox has zero call sites left in src/. Merged via #1137.
#1100 backend data-model

Two running tasks crash every endpoint that resolves the running task

Resolved

get_running_task ends in scalar_one_or_none(), which raises on more than one row — and nothing stops a second row existing, because _push_task skips the single-running-task rule that create_task enforces. Two devices each starting a task offline is enough. The result is a 500 from every caller including reads, and the user can't recover: the views that would let them stop a task are the ones erroring.

Three parts, all needed — make the read defensive (order_by(start_time.desc()).first()) so existing broken accounts unwedge immediately; close the write path in _push_task with a per-record conflict rather than a raise; add the partial unique index with a data-repair migration that runs before the constraint.
backend/app/services/db_service.py:441 sync_service.py:352 routers/pebble.py:58 mcp/time_tracking.py:64
All three parts landed, plus a savepoint in _add_task_or_running_conflict beyond what was asked — a genuinely concurrent push now conflicts one record instead of aborting the batch. Migration 006_unique_running_task.py repairs before indexing. Merged via #1138.
#1099 backend perf

SSE pins a pooled DB connection per stream, exhausting the pool at ~15 tabs

Resolved

The events endpoint depends on get_session, a yield-dependency FastAPI only unwinds once the response finishes — which for a StreamingResponse means when the client disconnects. Auth runs a SELECT and never commits, so the connection sits idle-in-transaction for the life of the stream. Pool is 5 + 10 overflow, and each signed-in tab holds exactly one stream, so ~15 tabs across all users blocks every other request for the 30 s acquisition timeout.

Give the SSE route its own short-lived auth dependency that resolves the principal, closes its session, and returns a plain user id.
backend/app/routers/db_sync.py:128 routers/auth.py:139 database/engine.py:63 config/settings.py:54
get_principal_shortlived opens and closes its own session before the stream body runs; the route is @limiter.exempt. Auth semantics unchanged — get_authenticated_principal already rejected PATs, so the new dependency doesn't narrow anything. Merged via #1139.
#1101 frontend sync

Backup restore silently reverts on a synced account

Resolved

Two defects that compound. restoreAppBackup writes through the optimistic collection API, firing one un-awaited push per record, then calls window.location.reload() synchronously — aborting those pushes before even the outbox catch can run. And restored preferences keep their _updatedAt from export time, so any backup older than the server copy loses the last-write-wins comparison. The user watches the restore apply, the page reload, and their old data come back.

Stamp a fresh _updatedAt at restore time; apply sections via the direct-write path so no push handlers fire, then push once through buildKeepLocalReplacePayload and await it before reloading.
frontend/src/utils/appBackup.ts:410 appBackup.ts:499 appBackup.ts:411 utils/syncClient.ts:741
Fresh _updatedAt stamped at restore; restoreAppBackup is now async, pulls once, pushes one buildKeepLocalReplacePayload, and window.location.reload() is unreachable unless that push succeeds. Merged via #1140.

#1103 backend frontend

First-sync filter drops invalid labels but keeps the tasks referencing them

Resolved

The defensive filter in buildLocalSyncPushPayload exists so "a single corrupted label cannot cause the entire first-sync push to fail" — but it drops labels and gantt tasks independently of the tasks pointing at them, leaving dangling references. Server-side that raises ValidationError, which 400s the whole batch, and since 400 is classified permanent it's quarantined rather than retried. One bad label costs the user their entire history upload, permanently.

Make the filter reference-aware: null out any label_id / gantt_task_id not in the surviving id sets.
frontend/src/utils/syncClient.ts:790 backend/app/services/sync_service.py:227 routers/db_sync.py:76
buildLocalSyncPushPayload now computes the surviving label and gantt-task id sets before building tasks/templates, and nulls out any label_id / gantt_task_id not in those sets (including a gantt task's own dangling label_id) instead of leaving the reference intact. Fixed in PR #1147.
#1102 backend observability

Postgres LISTEN never reconnects, so live updates die after a restart

Resolved

sse_manager opens its listen and notify connections once at startup and never re-establishes either — no termination listener, no supervised retry, no health check. After a Postgres restart or failover a worker stops delivering sync_changed permanently, with no log line, because nothing notices. The existing fallback doesn't help: it's local-only, and when another worker's notify connection is alive the NOTIFY "succeeds" so no fallback fires anywhere.

Register add_termination_listener on both connections with a backoff reconnect, mirroring _periodic_jwks_refresh_loop. Cheap interim: always call _enqueue_local alongside _pg_notify. Either way AGENTS.md is currently wrong about this and needs correcting.
backend/app/utils/sse_manager.py app/main.py:88 AGENTS.md — Live Updates
Both connections now register an asyncpg add_termination_listener that schedules _reconnect_with_backoff (exponential backoff, capped at 60s) on an unexpected drop, re-opening the connection and re-registering the channel listener; a _closing flag distinguishes a deliberate stop_pg_listener close from a real outage so shutdown doesn't itself trigger a reconnect. backend/app/utils/sse_manager.py; AGENTS.md's Live Updates section corrected to describe the reconnect behavior instead of claiming only in-process fallback. Fixed in PR #1146.
#1104 backend auth

Pebble clock-in/out commits without an audit entry

Resolved

pebble.py calls create_task / update_task without an actor, and _audit returns early when the actor is None — so the mutation commits with nothing staged. Every other mutating router passes one; this is the sole exception, and it's the one path using a long-lived delegated wtpat_ credential, which is exactly where you'd want the trail. Both the AuditEntry docstring and _audit's own docstring claim this can't happen.

Pass actor=audit_actor_for(principal) at both call sites. Separately: push_changes writes no audit entries at all — plausibly deliberate for bulk sync, but it needs a decision and a comment either way.
backend/app/routers/pebble.py:76 pebble.py:99 services/db_service.py:82
Both pebble_clock_in and pebble_clock_out now pass actor=audit_actor_for(principal), so PAT-authenticated writes land in audit_entries with auth_source="delegated". backend/app/routers/pebble.py. The push_changes bulk-sync gap was a deliberate decision, not an oversight: it's now documented with a comment on sync_service.push_changes and a qualifying note on the AuditEntry docstring in backend/app/database/models.py.
#1106 mcp auth

MCP reports rate-limit exhaustion as 401 invalid credentials

Resolved

verify_token catches RateLimitExceededError and returns None, which FastMCP turns into a 401. A throttled client is told its credentials are wrong, so instead of backing off it re-authenticates or rotates its key — and because the window rolls, it looks like an intermittent auth fault. The REST side gets this right with a real 429.

Either move enforcement out of token verification into a post-auth dependency, or let the error propagate and map it to a 429 with Retry-After computed from the stored window start.
backend/app/mcp_server.py:100 services/integration_client_service.py:221
Enforcement moved out of DbIntegrationClientVerifier.verify_token — it now only looks up the client, checks scope, and records usage. A new IntegrationClientRateLimitMiddleware runs after FastMCP's auth middleware resolves get_access_token() but before RequireAuthMiddleware's 401 gate, so an over-limit request gets a real 429 with a Retry-After header computed from the stored window start, never folded into "invalid credentials". Wired up via a new create_mcp_http_app() helper in backend/app/mcp_server.py, used by backend/app/main.py.

#1145 frontend

Resolved

What's already good

Recorded so it isn't disturbed.
