# Architecture

How the code is organised. The same layout is used in champagnefestival, daynest, travel and worktime, so a developer who
knows one of them finds things in the same place in the others. Only the feature (domain) folders differ.

## Frontend (`frontend/src/`)

```
main.tsx, vite-env.d.ts entry point and ambient types; nothing else lives loose in src/
app/                    bootstrap and app shell: providers, router (route tree, lazy pages), layout, home, pwa
features/<domain>/      one folder per business domain: pages (*Page.tsx), components used only there, hooks,
                        feature-only helpers and types, and the API calls of that domain
components/             shared UI used by two or more features; components/ui/ holds the design-system primitives
hooks/                  shared hooks used by two or more features
lib/                    framework-agnostic helpers by topic (lib/api/, lib/db/, lib/schedule/ ...); no `utils/` folder
mocks/                  MSW handlers, scenarios and fixtures (fixtures are typed with the generated API types)
config/                 runtime configuration and constants (OIDC, storage keys, app version)
types/                  UI-only types (never API shapes)
paraglide/              compiled messages (generated)
styles/                 global CSS (tailwind.css, app.css, tokens.css ...)
api-schema/             generated by Orval, never edited   api-types.ts   the single import point for API shapes
```

Rules:

- A folder under `features/` is named after the product domain, in kebab-case. Split one that grows past about 40 files
  into sub-folders by sub-area (`features/calendar/` does: `month` and `unified`; `features/settings/` is at the limit and
  already has `account`, `admin`, `data`, `hooks` and `time-tracking`).
- Code used by one feature stays in that feature. Move it to `components/`, `hooks/` or `lib/` only when a second feature
  needs it.
- Import across folders with the `@/` alias (`@/features/settings/SettingsPage`); use relative imports only inside one
  feature folder (at most one `../`).
- A feature does not import another feature; `app/` composes them (the route tree, the home tabs, the layout that hosts
  the onboarding wizard and the sync dialogs). `tests/architecture/featureBoundaries.test.ts` enforces it. Anything two
  features need goes to `components/`, `hooks/`, `lib/`, `config/` or `app/providers/`.
- API shapes come from `@/api-types` (generated types). Never declare an API response type by hand.
- Component files are `PascalCase.tsx`, hooks `useThing.ts`, other modules `camelCase.ts`.
- Tests live in `frontend/tests/` and mirror the `src/` path (`src/features/status/CurrentStatus.tsx` is covered by
  `tests/features/status/CurrentStatus.test.tsx`); shared helpers are in `tests/utils/`, global setup is `tests/setup.ts`.
  End-to-end specs are in `frontend/e2e/`.

### Exceptions

- `lib/hday/` keeps its path: the `.hday` helper (`hday-helper/`) imports `frontend/src/lib/hday/` directly and bundles it
  without the `@/` alias, so `lib/hday/parser.ts` uses a relative import of `config/timeOff.ts`, and the CI path filters
  name `frontend/src/lib/hday/**`.
- `lib/db/` (TanStack DB collections and their persistence) and `lib/sync/` are technical layers used by the providers
  and by several features, so they sit in `lib/` with their own `README.md` describing the data standard.
- The context providers live in `app/providers/` (`SettingsContext`, `EventStoreContext`, `AuthContext` ...) and are
  imported by the features; they are the shared state of the app, not a feature of their own.
- `lib/` has sub-folders by topic: `api/` (HTTP client and error mapping), `dates/`, `db/`, `events/`, `hday/`,
  `hday-helper/`, `push/`, `query/`, `schedule/` (rosters, shift and working-day maths), `storage/`, `sync/`,
  `time-off/` and `time-tracking/`; `logger.ts` and `utils.ts` (the shadcn `cn` helper that `components.json` points at)
  stay loose.
- `types/` is kept for the UI-only shapes several features use (countries, work location, public holidays, gantt) and the
  `frappe-gantt` typings; `types/countries.ts` is also read by a backend test, so it keeps its path.

### Features

| Folder          | What it holds                                                                                              |
| --------------- | ---------------------------------------------------------------------------------------------------------- |
| `auth`          | the OIDC callback and silent-renew pages (`/auth/callback`, `/auth/silent-callback`)                       |
| `calendar`      | the two calendar tabs: `month` (shift and time-off month grid) and `unified` (Schedule-X)                  |
| `gantt`         | the Gantt tab: chart, table, task modal and their helpers                                                  |
| `legal`         | `/privacy`                                                                                                 |
| `onboarding`    | the welcome wizard and its steps                                                                           |
| `pebble`        | `/pebble-pair`                                                                                             |
| `schedule`      | the schedule tab: today and week views, team transfer view                                                 |
| `settings`      | `/settings`: the sections, account/admin/data areas, backup, changelog dialog, and the label and template panels |
| `status`        | the current-status card (shift status, countdowns, flex start)                                             |
| `sync`          | the first-sync and ongoing-sync conflict dialogs, the sync status indicator and the first-sync flow       |
| `time-off`      | the time-off tab: views, import preview, vacation maths, and the team schedule view                        |
| `time-tracking` | the time-tracking tab: daily and weekly views, charts, timeline and their hooks                            |

`app/` holds `App.tsx`, `router/` (route tree, `lazyRoute`, route status and the not-found page), `home/` (the home page
and its tabs), `layout/` (app layout, header, about and keyboard-shortcut dialogs), `providers/`, `pwa/` and `hooks/`
(hooks only `App.tsx` uses).

## Where does new code go?

- A new page or screen: `features/<domain>/<Name>Page.tsx`, lazy-loaded and registered in `app/router/router.tsx`. A new
  home tab: its view in the feature, the tab in `app/home/MainTabs.tsx`.
- A component only one feature uses: that feature's folder. A second feature needs it: `components/`.
- A design-system primitive (a Base UI / shadcn wrapper): `components/ui/`, recorded in `ui-maintenance.json`.
- A hook or helper only one feature uses: that feature's folder. Shared: `hooks/` or `lib/<topic>/`.
- An API call or query hook: next to the feature that owns it; shared ones go to `hooks/` or `lib/api/`. Sync-managed
  data goes through `lib/db/collections.ts` (see `lib/db/README.md`).
- A provider, router change or layout piece: `app/`.
- MSW handlers and fixtures: `mocks/`. Constants and runtime configuration: `config/`. Storage keys: `config/storageKeys.ts`.
- A test: `frontend/tests/` at the mirrored path; a helper used by several tests: `tests/utils/`.

## Backend (`backend/app/`)

The backend keeps its current layout for now (`routers/`, `services/`, `models/`, `schemas.py`, `mcp/`, `middleware/`,
`core/` and a few flat modules). The shared target, applied to all four apps in a later step, is `main.py`, `core/`, `db/`,
`models/`, `schemas/`, `routers/`, `services/`, `mcp/` and `middleware/`.
